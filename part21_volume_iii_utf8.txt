## PART 21 — CHAT, CONVERSATION TABS, MESSAGE ARCHITECTURE AND CONTEXT MANAGEMENT

### 21.1 PURPOSE

The GSIR Chat system shall provide the primary interactive interface between the user and the GSIR AI system.

It shall support:

- Standard conversations

- Scientific research conversations

- Project conversations

- Multiple simultaneous conversation tabs

- Search

- AI modes

- Model selection

- File attachments

- Web research

- Scientific evidence retrieval

- AI reasoning

- Streaming responses

- Message editing

- Regeneration

- Branching

- Conversation history

- Conversation export

- Conversation memory

- Conversation-to-Project integration

- Conversation-to-Notes integration

The Chat subsystem must remain modular and must communicate with the AI Gateway rather than directly implementing model-provider logic.

END OF 21.1

The basic architecture shall be:

Frontend Chat

↓

Chat API

↓

↓

↓

↓

↓

↓

↓

↓

Frontend

Scientific research requests may additionally use:

Research Request

↓

↓

↓

↓

↓

END OF 21.2

### 21.3 CONVERSATION IDENTIFIER

Every conversation shall have a stable:

conversation_id

Recommended format:

conversation_<unique_identifier>

The identifier must remain unchanged throughout the conversation lifecycle.

END OF 21.3

### 21.4 MESSAGE IDENTIFIER

Every message shall have:

message_id

Recommended format:

message_<unique_identifier>

Every message must reference its conversation_id.

END OF 21.4

RESEARCH

The internal roles may not all be directly exposed to the user.

### 21.8 MESSAGE TREE

The architecture must support branching conversations.

Example:

User Message

     │

     └── AI Response A

           │

           ├── User Follow-up

           │

           └── Regenerated Response B

Therefore messages should support:

parent_message_id

This allows multiple response branches without destroying previous responses.

END OF 21.8

### 21.9 CHAT TAB ARCHITECTURE

The frontend shall support browser-like conversation tabs.

Example:

[ Solved Problem × ]

[ Number Systems × ]

[ Research Hypothesis × ]

[ New Chat + ]

Each tab must maintain:

conversation_id

title

selected model

selected mode

project_id

draft message

UI state

END OF 21.9

### 21.10 TAB STATE

Tab state should remain primarily client-side.

Example:

{

  "conversationId": "...",

  "title": "Research Hypothesis",

  "modelId": "...",

  "mode": "research",

  "projectId": "...",

  "draft": "..."

}

The backend remains authoritative for persisted conversation and message data.

END OF 21.10

NEW CHAT

↓

Create local conversation state

↓

User enters first message

↓

Create persistent conversation

↓

Persist message

↓

A completely empty tab does not need to create unnecessary database records immediately.

END OF 21.11

### 21.12 CHAT MODES

The Chat subsystem shall support a configurable mode architecture.

Initial modes:

AUTOMATIC

CHAT

ANALYSIS

RESEARCH

SCIENTIFIC

PROJECT

The mode determines orchestration behavior rather than merely changing the visual interface.

END OF 21.12

### 21.13 AUTOMATIC MODE

Automatic mode shall determine the appropriate execution strategy based on the request.

Conceptually:

User Request

↓

Intent Detection

↓

Complexity Assessment

↓

Required Tools

↓

Required Context

↓

Select Execution Strategy

Automatic mode must not unnecessarily invoke expensive tools or models.

END OF 21.13

### 21.14 CHAT MODE

Chat mode is intended for ordinary conversational requests.

It should minimize unnecessary:

web searches

retrieval

long reasoning chains

tool calls

expensive models

END OF 21.14

### 21.15 ANALYSIS MODE

Analysis mode should support deeper structured analysis.

Possible operations:

problem decomposition

comparison

reasoning

data interpretation

structured synthesis

The mode should use the AI Gateway and reasoning architecture defined elsewhere.

END OF 21.15

### 21.16 RESEARCH MODE

Research mode shall support:

question decomposition

web/source retrieval

source comparison

evidence extraction

citation tracking

conflict detection

synthesis

uncertainty identification

Research mode must not treat search results as automatically validated scientific facts.

END OF 21.16

It may retrieve:

Project Notes

Hypotheses

Persist Message

END OF 21.21

### 21.22 STREAMING

The Chat system shall support streaming AI responses.

The frontend should receive incremental response events rather than waiting for the complete response.

Example:

response.started

response.delta

response.delta

response.delta

tool.started

tool.completed

response.delta

response.completed

The exact event contract shall be defined by the global AI streaming architecture.

END OF 21.22

### 21.23 STREAM INTERRUPTION

If a connection is interrupted:

Frontend

↓

Reconnect

↓

Request stream state

↓

Resume or retrieve completed response

The system must avoid duplicating message content.

END OF 21.23

### 21.25 MESSAGE EDITING

Editing must not silently overwrite the original research history.

Preferred behavior:

↓

├── Response A

└── Response B

### 21.36 CHAT MEMORY

Conversation memory and long-term memory must remain separate.

Conversation context:

Current conversation

Project memory:

Current Project

User memory:

Authorized persistent user information

The system must not merge these scopes indiscriminately.

END OF 21.36

### 21.37 CONTEXT WINDOW MANAGEMENT

↓

+

+

↓

### 21.38 CONTEXT SUMMARIZATION

Important research evidence should retain source references and should not be reduced to unsupported summaries.

### 21.48 OFFLINE AI

If the user has downloaded an approved local AI model:

Chat

↓

Model Capability Check

↓

Local Model Available?

├── Yes → Local Model

└── No → Remote AI Gateway

Offline mode must respect the model's capabilities and the user's selected privacy settings.

Cloud-only tools such as live Web Search cannot function without connectivity.

END OF 21.48

### 21.49 MODEL SELECTION

The frontend should not hard-code provider-specific logic.

It should send:

model_id

The backend Model Registry determines:

provider

capabilities

context capacity

cost class

availability

local/remote status

The Model Router makes the final execution decision.

END OF 21.49

### 21.50 COST-AWARE CHAT EXECUTION

Chat execution should avoid unnecessary expensive operations.

The system may use:

small models for classification

cached results

retrieval before generation

local models

streaming

prompt compression

context filtering

model routing

batch processing where appropriate

Expensive models should be reserved for requests requiring their capabilities.

END OF 21.50

### 21.51 ERROR HANDLING

Possible errors:

authentication failure

authorization failure

invalid request

model unavailable

provider timeout

rate limit

tool failure

network interruption

context retrieval failure

file processing failure

AI generation failure

The user should receive a useful controlled error without exposing internal secrets or infrastructure details.

END OF 21.51

### 21.52 RETRY POLICY

Retries must be controlled.

Transient failures may be retried.

Permanent failures should not be repeatedly retried.

Examples of potentially retryable failures:

network timeout

temporary provider error

temporary service unavailable

The retry system must use exponential backoff and retry limits.

END OF 21.52

### 21.53 IDEMPOTENCY

AI request submission should support idempotency.

Each generation request may include:

request_id

idempotency_key

This prevents duplicate AI generations when clients retry after network interruptions.

END OF 21.53

### 21.54 CHAT CONCURRENCY

Multiple conversations may execute simultaneously.

The system must isolate:

conversation state

request state

stream state

model state

tool state

A slow conversation must not block unrelated conversations.

END OF 21.54

### 21.55 SCALABILITY

The Chat architecture must be horizontally scalable.

Stateless API workers should handle requests while persistent state is stored in appropriate infrastructure.

Long-running AI operations should be handled through asynchronous job infrastructure where appropriate.

Streaming connections should be managed independently from database operations.

END OF 21.55

### 21.68 CHAT ACCEPTANCE CRITERIA

Part 21 shall be considered implemented only when:

- Users can create conversations.

- Users can open multiple chat tabs.

- Each tab maintains independent state.

- Conversations have stable IDs.

- Messages have stable IDs.

- Messages support branching.

- Messages can be edited.

- Responses can be regenerated.

- Responses stream correctly.

- Generation can be stopped.

- Interrupted streams can recover safely.

- Chat history works.

- Chat search works.

- Project conversations work.

- Notes can be created from messages.

- Files can be attached.

- Models can be selected through model IDs.

- Chat modes work through the orchestration layer.

- Research mode can invoke the research architecture.

- Web Search can be controlled through settings and permissions.

- Tools use the centralized tool architecture.

- Plugin operations use the centralized plugin architecture.

- Offline models can be selected when available.

- Context is managed without unnecessarily loading complete histories.

- Conversation memory remains distinct from Project and user memory.

- Research citations remain traceable.

- Unauthorized data cannot enter AI context.

- Prompt injection from external content is isolated.

- API responses follow the common GSIR contract.

- Chat state is scalable and concurrency-safe.

- Failures are handled without data loss.

- Chat operations are observable.

- Automated tests cover the complete Chat lifecycle.

- Chat integrates correctly with AI Gateway, Model Router, Projects, Notes, Files, Search, Research, Memory, Tools and Plugins.

END OF PART 21
